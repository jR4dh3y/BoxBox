# BoxBox v0.4.0 release checklist

Changes since v0.3.2 include OIDC sign-in (#250), share link previews (#249), per-account NAS identities (#266), delete-on-share-expiry (#267), and cross-disk moves that preserve symlinks and modes (#268). The release also includes the native GPUI `boxbox` desktop app, the replacement for Electrobun with a Windows x64 package (#248), and the web file-manager updates (#272).

## 1. Prepare the release commit

- [ ] Set the root `VERSION` to `0.4.0`. The tag workflow, release archive names, manifest, and Windows packaging use this value.
- [ ] Update `docs/release.md` to use `docs/releases/v0.4.0.md` and `v0.4.0` in the stable release instructions and `v0.4.0-rc.1` in the optional prerelease example. Keep the v0.3.2 Electrobun history and AppImage cutoff.
- [ ] Finish `docs/releases/v0.4.0.md` for GitHub and the v0.4.0 section of `docs/release-notes.md` for the site. Describe the upgrades and actual package targets. Check any security heading against the changes and remove it if there is no release-specific security fix to announce.
- [ ] Arrange the website rollout before merging into the production branch. If Vercel deploys automatically from `master`, hold production deployment or keep the blog commit out of the release merge and land it after publication. The nav, blog index, and post are generated during the website build, so any production deploy containing the blog commit exposes the newest post immediately.

Keep the following files at their existing versions:

| Files | Reason |
| --- | --- |
| `desktop/build.rs`, `desktop/src/workspace/about.rs`, `desktop/UI_MAP.md` | The v0.3.2 references illustrate or test version formatting. About uses `git describe` and falls back to `VERSION` when tags are unavailable. |
| `desktop/Cargo.toml`, `desktop/Cargo.lock` | The unpublished desktop crate uses `0.0.0`; matching `0.3.2` entries in the lockfile are dependency versions. |
| `packaging/aur/PKGBUILD` | The tracked template has a version/checksum pair. After publication, `scripts/prepare-aur.sh` generates the AUR copy with `pkgver=0.4.0` and the v0.4.0 archive checksum. |
| `docs/releases/v0.3.2.md`, `docs/evidence/desktop-release-v0.3.2.md`, v0.3.2 section of `docs/release-notes.md` | Prior release notes, asset links, and validation evidence are historical. |
| `docs/desktop.md`, `.github/workflows/appimages.yml` | v0.3.2 is the pairing API minimum and the final Electrobun release. |
| `.github/scripts/test_check_release.py`, `.github/scripts/test_ci_scope.py`, `website/src/lib/releases.test.ts` | The versions are test fixtures for tag validation, a docs path, and release asset parsing. |
| `website/src/lib/demo/sample.ts` | Both references belong to the sample filesystem. The release notes sample describes v0.3.2. |
| `frontend/bun.lock`, `website/bun.lock` | Matching text belongs to dependencies and lockfile hashes. |

## 2. Validate, merge, and tag

- [ ] Confirm the desktop app keeps the `boxbox` name everywhere before tagging: the Linux binary and `install.sh`, the desktop entry, the AppImage, the AUR package contents, and `boxbox.exe` in the Windows ZIP. Nothing should ship as `boxbox-files` or `io.boxbox.files`.
- [ ] Run the release checks in [the release workflow](../release.md). A `test/*` branch image can exercise a deployment, and manual release workflow dispatch can build CI artifacts. Check the Linux installer and Windows x64 ZIP on their target systems.
- [ ] Land #248 and #272 in `master` along with the reviewed version and release-note changes. Wait for CI and confirm the intended commit is on `origin/master`, has `VERSION=0.4.0`, contains `docs/releases/v0.4.0.md`, and includes all changes in scope.
- [ ] From the tested `master` commit after `git pull --ff-only`, create `git tag v0.4.0` and publish it with `git push origin v0.4.0`. Use a new patch tag for a hotfix after publication.

## 3. Verify publication

- [ ] Wait for **Publish BoxBox Release** to validate the source, server, web app, website, Docker build, and desktop packages. Confirm GHCR publishes the amd64 and arm64 image for `v0.4.0` and moves stable `latest`. Nightly uses its own GHCR package.
- [ ] Confirm the GitHub release is public and points to the tested tag. The workflow waits for package and Docker jobs, uploads to a draft, then makes it public. Check the Linux x86_64 desktop tarball, Windows x64 desktop ZIP, amd64 and arm64 server archives, `SHA256SUMS`, and `release-manifest.json`. Verify the manifest and checksum file include the Windows ZIP.
- [ ] Check the follow-on AppImage and AUR jobs. Verify x86_64 and ARM64 AppImages and their checksum files on the release. Verify AUR published `boxbox-bin 0.4.0-1` from the public Linux desktop archive after the Arch build and namcap checks. The AppImage and AUR workflows accept an existing release tag for manual retries.

## 4. Update the install default and publish the website

- [ ] In `docker-compose.yml`, change the default image pin to `ghcr.io/jr4dh3y/boxbox:v0.4.0` after the image is available. Quick Start fetches Compose directly from `master`, so keep its existing pin while the new image is building.
- [ ] Replace the draft in `website/src/blog/v0-4-0.md`, set the publication date in `website/src/lib/blog.ts`, and add approved images under `website/public/blog/v0.4.0/`. Build and check the final site.
- [ ] Deploy the website only after the v0.4.0 GitHub release is public. If the post refers to AppImage or AUR availability, verify those channels first. Confirm the production nav links to `/blog/v0-4-0/` without JavaScript, the post and images load, and `/download/` shows the v0.4.0 assets once the release API cache refreshes.
