Ownership policy and implementation:
- Newly restored records use SHA-256 + '.' + encodeURIComponent(username).
  The username is the session owner already captured by the login queue. The
  hash, source metadata, server protocol and IndexedDB schema version stay put.
  Separators and Unicode remain injectively encoded; the fixed-length hash
  precedes the separator. The existing local-reference parser accepts this form.
- Each account has distinct bytes and object-URL cache entries even when hashes
  match. Ordinary local uploads retain their existing fresh random IDs.
- Old hash-only records have unknown ownership. Keep them readable and never
  delete them through automatic cleanup. A successful restore copies their
  bytes into the account-owned record before changing preferences, including
  when downloading is unavailable. Other accounts can keep using the legacy
  record until their own restore succeeds. This deliberately retains old shared
  records instead of introducing reference counting or unsafe ownership guesses.
- Cleanup still deletes owned records and random upload records. Clear, Reset,
  replacement, aborted staging and authoritative login cleanup share this API.
- Non-hashing browser comparison accepts both legacy and scoped hash IDs.
  Secure-origin comparison continues hashing actual bytes. Removed unused
  duplicated MIME/date fields from new records; Blob already owns MIME type,
  and no reader uses creation time. Old records remain readable.
- Picker and publication scripts protect startup and launch with their existing
  cleanup flow. Nested finally blocks ensure close failure cannot skip server
  stop, and stop failure cannot skip root removal. No resource framework added.
- Retry verification polls for both 200 and exact expected image bytes with a
  10-second deadline. Exact final body equality is retained. The other-tab case
  starts with a different real image returning 200, so status alone cannot pass.
