State and ownership:
- WallpaperPublication is absent | pending(id, source:string|null) |
  completed(id). null is an explicit removal, not an absent operation.
- SettingsStore.set with explicit image intent, and Reset, record pending intent
  synchronously in the same call that applies/persists local settings. There
  is no paint, queue, IndexedDB, network or other await between intent and apply.
- A 128-bit random operation ID works without secure-context randomUUID.
  The captured ID travels from local apply through Save/Reset and the queue.
  Transport may reconcile only that current pending ID and matching source.
  A queued operation cannot adopt a same-source successor or edit a completed
  successor's display. Login retries explicitly capture the current ID.
- Each account has one latest-intent pointer. A transport acknowledgement writes
  only its operation's durable receipt; it never overwrites the latest pointer.
  This avoids a cross-tab read/check/write race on completion. The public
  interface remains read/begin/complete over the single publication union.
- Every state read checks the durable pointer and, for pending state, its
  receipt. A different raw pointer replaces memory fallback, including when a
  new session observes another tab's intent. No storage-event delivery timing
  or permanent process-wide cache takes precedence over newer durable data.
- Memory fallback is tied to the last observed durable raw pointer. Failed
  set/get operations retain local pending/acknowledged state while that pointer
  is unchanged. Completion is never cleared on logout. Receipt cleanup occurs
  only after a new pointer was successfully written, and only for the replaced
  completed operation. Failed cleanup cannot reveal an older pending pointer.
- Old nonempty pending-source keys and empty completed keys remain readable.
  Old pending operations acquire their own durable receipt when retried.

Transition proof:
- Before apply: page/session cancellation after a progress paint or IndexedDB
  completion prevents preference/intent mutation. The staged local image is
  deleted by its owning Save. Logout, same-user relogin, B login and unmount
  retain the previous cancellation boundaries.
- Apply: pending(id, image) or pending(id, null), local settings, and ownership
  transfer of staged bytes happen without yielding. Old-image cleanup starts
  immediately after apply so page navigation cannot strand that cleanup behind
  the publication queue. It never cleans up the newly applied image.
- After apply: paint cancellation, page disposal or canceled queued transport
  leave pending intent and its current image bytes intact. Reload/login retries
  the owned image or deletion before remote restoration, including a remote 404.
- Failed transport: pending remains; no acknowledgement is manufactured.
- Successful transport: receipt(id), then matching in-memory completed(id).
  A completion for A cannot complete, clear or hide B's pending operation.
- New durable operation: its unique ID invalidates any old completed fallback,
  even if its source matches. External receipts are observed from cached pending
  state. Superseded queued work does not publish the newer operation.
- Completed + authoritative remote deletion: removal wins; no PUT resurrects
  the completed image, including when pending-key removal or completion writes
  are blocked. A failed completion write is not reported as a transport failure.
