GTK/GObject signal, cache, and lifetime plumbing is grouped as `—` only where it creates no separate user behavior; the `ThunarxFileInfo` rows are the plugin API.

## Missing or partial, ranked
1. **Missing capability metadata and permissions** (rows 23–25): Linux users need to see ownership, rwx bits and whether rename/trash/write actions are actually allowed before attempting them.
2. **Partial filesystem integration** (rows 3, 14): the app handles local paths and BoxBox servers but not the broader GIO URI/back-end model or URI-aware launching.
3. **Partial drop behavior** (rows 27–30): native file managers need folder targets and copy/move decisions that match source/target filesystem capabilities; UI_MAP already tracks row/tile and in-app drops.
4. **Partial MIME and desktop-entry behavior** (rows 4–13, 33): MIME-based types and complete desktop-entry trust, launch, and chooser semantics are central to opening Linux files safely and predictably.
5. **Partial per-directory state and sorting** (rows 32–36): users expect MIME type sorting, more metadata sort keys, and folder-specific view/sort preferences.
6. **Partial live directory updates** (rows 42–44): GPUI refreshes at a 500 ms polling cadence and replaces the list wholesale, so rapid changes and file identity updates can lag Thunar.
7. **Partial freedesktop thumbnails and retry behavior** (rows 18, 38–39): shared cache reuse and retries affect consistency with other Linux apps and responsiveness on large folders.
8. **Partial trash metadata and recents** (rows 15, 37): deletion date readability, Trash fullness and Recent integration are common file-manager cues.
9. **Partial hidden-file and date metadata** (rows 16, 22): backup files and dates beyond modification time are useful for inspection and recovery.
10. **Missing alternate-display launch utility** (row 47): useful only for launchers or scripts that explicitly choose a GDK display.
